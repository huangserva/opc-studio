## 1. 修复与取舍

旧实现把 `title LIKE` 写在 WHERE 中，LIMIT 51 只能限制命中数，稀有短词仍可能遍历 29 万份资料。本次采用合同方案②，将匹配条件作为每行的计算结果，按既有 rowid 倒序读取，每读取一条记录立即处理，最多检查 8192 条，并以 monotonic 时钟限制为 0.25 秒。SQLite progress handler 每 256 条 VM 指令检查同一截止时间；超时只捕获 SQLITE_INTERRUPT，保留之前已取得的结果，其余数据库错误仍按原路径抛出。

无需预热或查询结果缓存；每次用原来的 mode=ro 连接。未创建旁路文件，未写表、未建索引、未读取 body、未全表 COUNT。长词仍使用原来的 trigram FTS + snippet。

命中最多返回 50 条，额外一条仅判断下一页；总数仍为下界，部分搜索的空页显示「≥0」而非把页码偏移伪装成已找到的数。响应增加 `partial` 和 `scanned_count`；页面同时显示「只搜了最近 N 条资料，换长一点的词可全库搜」，空页显示「本次检查的资料中没有找到」。完整检查完小库时不冒称部分搜索。

能力边界：短词可能漏掉扫描窗口之外的旧资料，或在时间预算先到时检查少于 8192 条；页面如实告知。输入至少 3 个字可继续全库 FTS 检索；未引入后台同步和同步失败模式。此限制为合同明确允许的方案。
